당신은 이 프로젝트의 구현 책임자다.
아래 명세에 따라 설계, 병렬 구현, 실행, 검증, 수정, 문서화까지 수행하라.
계획이나 코드 생성만으로 종료하지 말고, 마감까지 실제로 동작하는 로컬 시연과 배포 준비를 완성하라.

## 0. 실행 변수와 최우선 조건

PROJECT_ROOT = <대상 프로젝트의 실제 절대 경로>
WORK_ROOT = PROJECT_ROOT 바로 아래의 trading 디렉터리
DEADLINE = 2026-09-22 09:00:00 Asia/Seoul (UTC+09:00)

- 프로젝트 경로는 위 PROJECT_ROOT 한 곳에서만 지정한다.
- 시작 시 실제 절대 경로, 현재 시각, 남은 시간을 확인하고 기록한다.
- PROJECT_ROOT가 입력되지 않았거나 대상이 불명확하면 경로만 질문한다. 현재 디렉터리를 임의로 대상 프로젝트로 간주하지 마라.
- 구현과 프로젝트 산출물 작성은 WORK_ROOT 안에서 수행한다.
- 이번 납품 범위는 로컬 시연, 검증 증거, Vercel 프런트엔드 및 별도 Rust 엔진의 배포 준비다.
- 실제 외부 배포와 trading 외부 파일 수정은 별도 명시적 지시 없이 수행하지 않는다.
- 마감 전까지 추가 지시를 기다리지 않고 의미 있는 구현·검증·개선 작업을 지속한다.
- 마감과 전체 요구사항 충족 여부는 구분한다. 미완료 항목이 있어도 09:00 전에 실제 상태와 결과를 제출한다.
- 이후 명세의 해석은 이 작업 경계와 마감 조건을 따른다.

## 1. 작업 경계와 권한

허용:
- WORK_ROOT 내부 코드·문서·테스트·설정 작성과 수정.
- 합성 데이터 생성, 로컬 실행, 테스트, 벤치마크, 장애 주입, 오류 수정.

- 프로젝트 루트의 AGENTS.md, 기존 코드, UI, 설정, 자산을 지침·연동 구조 파악 목적으로 읽기.

금지:

- trading 외부 프로젝트 파일의 임의 생성·수정·이동·삭제.
- 기존 데이터 삭제, 기존 변경 덮어쓰기, 파괴적인 Git 명령.

보존 및 경로:
- trading이 없으면 생성한다. 있으면 기존 내용을 먼저 확인하고 보존하며 확장한다.
- 기존 코드, 미커밋 변경, 문서, 자산, 데이터를 보존하고 재사용·확장을 우선한다.
- 코드, UI, 테스트, 스크립트, 배포 설정, 문서, ADR, 합성 데이터, 로그, 벤치마크 결과, 스크린샷과 시연 자료는 trading 하위에 둔다.
- 명령의 작업 디렉터리를 명시하고 빌드 도구가 루트 설정·lockfile 등을 의도치 않게 변경하지 않는지 확인한다.
- 프로젝트가 생성·관리하는 임시 파일과 빌드 산출물도 가능한 한 trading 하위로 설정한다.
- 개발용 하위 에이전트에도 동일한 작업 경계를 적용한다.
- 장애 주입은 전용 합성 데이터 또는 그 복사본에서 실행한다.
- 실행마다 고유 run ID를 사용하고 이전 실행의 증거를 덮어쓰지 않는다.
- 일반적인 구현 선택은 합리적인 기본값으로 진행하고 가정을 기록한다. 이미 허용된 작업에 반복 승인을 요청하지 마라.
- 추가 승인이 필요한 부분은 먼저 trading 안에 구체적인 변경안·패치·근거를 준비한다. 해당 승인에 의존하지 않는 작업은 계속 수행한다.

## 2. 마감까지의 지속 작업과 인계

지속 작업:
- 이 요청을 마감까지 이어서 수행할 작업으로 취급한다. 환경이 지속 목표·재개 기능을 제공하면 이 명세와 마감을 포함하여 사용하고 실제 설정·동작 여부를 기록한다.
- 계획 작성, 첫 실행 성공, 일부 기능 완성을 이유로 작업을 종료하지 마라.
- 사용자 응답이 없어도 허용된 독립 작업을 진행한다.
- 핵심 기능이 일찍 완성되면 거래·정산 불변조건, 동시성, 장애 복구, 장시간 시연, 메모리·지연 관찰, 측정된 병목, UI 사용성, 문서·증거를 순서대로 보완한다.
- 의미 없는 대기, 동일 테스트의 무의미한 반복, 무관한 기능 추가로 시간을 채우지 마라.
- 장시간 시연은 자원 사용량과 로그 증가량을 관찰한다. 로그 분할·용량 정책을 두되 기존 증거를 삭제하지 않는다.
- 실행 환경의 세션·사용량·시스템 제한을 프롬프트만으로 해소할 수 있다고 가정하지 마라.
- 실제로 중단된 기간을 작업 시간으로 기록하지 마라. 지속 실행이 제한되면 원인, 보존한 상태, 재개 방법을 기록한다.

모든 아래 시각은 2026-09-22, Asia/Seoul 기준이다.
- 07:00부터: 새로운 대형 기능과 구조 변경을 제한하고 통합·결함 수정·복구 검증에 집중한다.
- 08:00부터: 최종 검증, 시연 재현, 실행·배포 문서와 증거 정리를 우선한다.
- 08:30부터: 검증된 기능을 보존하고 치명적인 결함만 수정한다.
- 08:55까지: 제출 가능한 코드·문서·증거와 최종 보고를 준비한다.
- 09:00 전에: 마지막 상태와 인계 정보를 저장하고 최종 결과를 제출한다.
- 시작 시 이미 지난 구간은 건너뛰고 남은 시간에 맞춰 조정한다.
- 각 변경은 남은 시간 안에 검증까지 마칠 수 있는지 고려한다.
- 시작·재개 시 마감이 이미 지났다면 새 구현을 시작하지 말고 기존 기록을 확인하여 현재 결과·미완료 항목·재개 방법을 보고한다.
- 마감 이후에도 작업해야 한다고 임의로 판단하거나, 마감이 되었다는 이유로 미완료 요구를 완료 처리하지 마라.

## 3. 목표·기술 스택·배포 구조

목표:
그룹사 임직원이 합성 휴가 자산을 주식처럼 매수·매도하는 모의 휴가 거래소를 구현한다.
사용자는 실시간 차트·호가·체결·가격을 보면서 주문하고, 거래 봇과 같은 시장에서 체결을 경험할 수 있어야 한다.

기술 스택:
- 프런트엔드: 기존 스택을 우선한다. 신규 구성이면 TypeScript + Next.js.
- 프런트엔드 배포 대상: Vercel.
- 매칭·주문 검증·정산·시퀀싱·저널·스냅샷·복구: Rust.
- 엔진 배포 대상: 상시 실행 가능한 별도 VM 또는 컨테이너 환경.
- 영속 데이터: 엔진 재시작·재배포 후에도 보존되는 저장소의 저널·스냅샷.
- 실시간 데이터 전달: WebSocket 등 요구사항에 맞는 이벤트 스트림.

구조 원칙:
- Rust 코어를 네트워크, 파일 I/O, UI와 분리하여 독립 테스트·벤치마크가 가능하게 한다.
- 서버가 권위 있는 거래 상태를 관리하고 모든 사용자와 봇은 같은 시장을 공유한다.
- Vercel Functions의 인스턴스 메모리를 전역 호가장·잔고의 영속 저장소로 사용하지 않는다.
- Vercel 기능을 사용할 때 현재 공식 문서에서 런타임 지원·빌드·실행 제약을 확인한다.
- 로컬과 배포 환경의 주문·이벤트 계약을 동일하게 유지한다.
- API·WebSocket 주소는 환경변수로 설정한다. 브라우저 번들에 서버 비밀정보를 넣지 않는다.
- 로컬 서비스는 기본적으로 localhost에 바인딩한다.
- 배포 구성은 HTTPS/WSS와 허용 Origin을 명시한다. 온라인 시연의 엔진 주소는 실제 접근 가능한 서버 주소를 사용한다.
- 배포된 화면에서 localhost가 각 사용자의 PC를 가리킨다는 점을 고려한다.

실행 형태:
A. 전체 로컬 시연: UI + Rust 엔진·API + 영속 데이터 + 12개 봇.
B. 배포 준비: Vercel UI + 별도 Rust 엔진 + 영속 저장소 설정·절차.
C. 온라인 시연 준비: 봇의 로컬·서버 실행 위치와 엔진 연결 방법 문서화.

실제 호스팅 가입·결제·외부 배포는 수행하지 않는다. 특정 사업자에 종속되지 않는 엔진 실행 구성을 제공한다.
Vercel 설정에는 실제 프런트엔드 디렉터리에 맞는 Root Directory와 빌드 명령을 명시한다.

## 4. 구현 우선순위

1) 기존 작업 보존과 거래·잔고 정확성.
2) 주문부터 화면 반영까지 작동하는 전체 흐름.
3) 내구성·복구와 재현 가능한 검증.
4) 측정에 근거한 성능 최적화.
5) UI 완성도, 배포 편의성, 문서 품질.

첫 실행 가능한 흐름:
주문 제출 → 검증 → 시퀀싱 → 매칭·정산 → 이벤트 → UI 갱신.

- 설계 문서만 장시간 작성하지 말고 작은 전체 흐름을 먼저 실행한다.
- 정확성을 희생하여 성능을 높이지 않는다.
- “완벽”, “초저지연”, “lock-free”, “zero allocation”에는 적용 범위와 검증 근거가 있어야 한다.
- 필수 요구를 임의로 제외하지 않는다. 마감 내 충족하지 못한 요구는 미완료로 보고한다.

## 5. 거래 규칙·요청 규칙·불변조건

기존 도메인 규칙을 먼저 확인한다. 아래 기본값과 충돌하면 내용을 기록하고 작업 경계 안에서 해결한다.
별도 규칙이 없다면 다음으로 구현한다.

거래 기본값:
- 최소 3개 그룹사의 합성 임직원 계정.
- 최초 상품은 동일 조건의 모의 휴가 시간 1종.
- 최소 거래 수량은 1시간, 가격은 정수형 모의 포인트.
- 실제 연차 권리 이전과 날짜별 휴가 승인·배정은 범위에서 제외한다.
- 가격·수량·잔고는 정수 또는 명시적인 고정소수점을 사용한다.
- 초기 휴가와 포인트 지급 이후 거래에서는 전체 자산 총량을 보존한다.
- 지정가 주문, 취소, 부분 체결, 여러 상대 주문과의 체결을 지원한다.
- 가격 우선, 동일 가격에서는 엔진 접수 순번 우선으로 매칭한다.
- 체결 가격은 호가장에 먼저 존재한 상대 주문 가격을 사용한다.
- 매수 주문의 포인트와 매도 주문의 휴가를 예약한다.
- 체결·취소·거절 시 예약·정산·해제를 정확히 수행한다. 가격 개선으로 남는 예약 포인트도 처리한다.
- 잔고 부족, 잘못된 가격·수량, 정수 오버플로를 처리한다.
- 자기 체결 방지 정책을 명시하고 구현한다.
- 주문 정정은 선택 기능이다. 추가하면 우선순위 유지·상실 규칙을 명시한다.

요청·계정 규칙:
- 클라이언트 요청 ID, 주문 ID, 명령 순번, 이벤트 순번을 구분한다.
- 중복 방지 키는 계정 ID와 클라이언트 요청 ID의 조합이다.
- 같은 키와 같은 요청 내용은 기존 처리 상태·결과를 반환하고 부작용을 중복 발생시키지 않는다.
- 같은 키에 다른 요청 내용이 들어오면 충돌 오류로 거절한다.
- 진행 중 중복 요청, 응답 유실, 재시작 후 재시도를 처리한다.
- 요청 ID 보존 기간·용량·만료 정책을 명시하고 보장 기간의 상태를 복구 후에도 유지한다.
- 주문 취소는 해당 주문의 소유 계정만 수행할 수 있다.
- 요청 계정 식별은 명시적인 로컬 모의 세션·계정 매핑으로 처리하고, 거래 봇과 수동 사용자의 계정을 구분한다.
- 단순 큐 접수 응답과 내구성이 확보된 성공 ACK를 구분한다.

핵심 불변조건:
- 사용 가능 잔고와 예약 잔고가 음수가 되지 않는다.
- 원주문 수량 = 누적 체결 수량 + 취소 수량 + 미체결 수량.
- 거래로 전체 포인트와 휴가 총량이 달라지지 않는다.
- 중복 요청이 주문·체결·정산을 중복 발생시키지 않는다.
- 호가장, 주문 상태, 체결 기록, 잔고·예약이 일치한다.
- 거절된 명령이 부분적인 거래 상태 변경을 남기지 않는다.

## 6. 엔진·동시성·메모리

구조:
- 단일 writer 기반 결정적 상태 머신을 우선 검토한다.
- 다중 클라이언트의 동시 제출을 지원하되 상태 변경 순서는 일관되게 유지한다.
- 동일한 초기 상태와 순서가 정해진 입력은 동일한 거래 결과를 생성한다.
- 시계·난수 등 외부 입력이 결과에 영향을 주면 재생에 필요한 값을 기록한다.
- 주문 접수·취소·체결·예약·정산의 원자적 변경 범위와 외부 관찰 시점을 정의한다.
- async 네트워크 처리와 매칭 코어의 실행 경계를 명확히 한다.

성능 구조:
- 엔진 hot path에서 mutex와 blocking I/O를 제거하는 구조를 목표로 한다.
- 스레드 간 전달은 검증된 bounded queue를 우선 검토한다.
- lock-free 보장은 채택한 자료구조와 적용 구간에 대해 확인한다.
- 주문 저장소와 이벤트 버퍼를 사전 할당하고 재사용한다.
- 정상 상태 hot path의 할당 횟수 0을 목표로 실제 계측한다.
- 네트워크·직렬화·로그·복구를 포함한 서비스 전체의 할당과 구분한다.
- 큐·주문·가격 범위·이벤트 버퍼의 용량을 설정과 문서에 명시한다.
- 용량 초과는 명시적인 거절 또는 backpressure로 처리한다.
- 한 주문이 많은 체결을 만들 때도 버퍼 부족으로 부분 상태가 노출되지 않게 한다.
- unsafe나 자체 lock-free 자료구조는 필요성과 검증 방법이 명확할 때만 사용한다.
- 언어 선택만으로 거래 원자성, 결정성, 무할당, 무장애가 보장된다고 주장하지 않는다.

## 7. Sequencing·Journaling·Snapshot·Recovery

시퀀스 부여, 저널 기록, 내구성 확보, 상태 반영, 응답·이벤트 공개의 순서와 장애 시 의미를 ADR로 고정한다.
구체적인 순서는 선택한 설계에 따르되 보장 사항과 모순되면 안 된다.

필수 기능:
- 단조 증가하는 엔진 명령 순번.
- 버전·레코드 경계·길이·무결성 검사를 포함한 저널.
- 재시작 이후에도 보장 기간 안에서 유지되는 요청 중복 방지.
- 기본 모드에서 성공 ACK한 거래의 복구 보장.
- 저널 write·flush·OS 동기화와 ACK의 관계 명시.
- batching 사용 시 지연·처리량·내구성 영향 명시.
- 내구성 확보에 실패한 요청에 성공 ACK를 반환하지 않는 오류 처리.
- 저널 I/O 실패 시 후속 주문 접수·처리 정책과 복구 절차.
- 프로세스 종료, OS 장애, 전원 장애에 대한 보장 범위 구분.
- 미응답 요청의 처리 여부 조회와 안전한 재시도.

스냅샷:
- 정확한 엔진 순번에 대응하는 일관된 상태를 저장한다.
- 호가장, 잔고·예약, 주문 상태, ID·순번, 중복 방지 상태를 포함한다.
- 불완전한 스냅샷이 정상 스냅샷으로 선택되지 않도록 저장·게시 절차를 구현한다.
- 유효한 스냅샷과 이후 저널로 복구한다.
- 복구 중 신규 주문 접수를 제어하고 복구 완료 상태를 노출한다.

장애 검증:
- 정상 종료 후 재시작.
- 거래 중 프로세스 강제 종료 후 재시작.
- 스냅샷 저장 중 중단.
- 저널 마지막 레코드의 부분 기록과 저널 중간 손상.
- ACK 전후 장애, 응답 유실 후 재시도, 저널 쓰기 실패.
- 원본 실행과 같은 확정 입력 범위를 재생한 결과의 주문·잔고·호가장 비교.

부분 기록과 중간 손상의 정책을 구분한다.
복구할 수 없는 손상을 조용히 무시하거나 증거를 삭제하지 않는다.
성공 ACK한 요청의 복구와 미응답 요청의 상태 확인을 각각 검증한다.
프로세스 강제 종료 테스트만으로 OS·전원 장애까지 검증했다고 보고하지 않는다.

## 8. 놀이공원 테마 UI·기존 화면 연동

- 프로젝트 루트의 기존 UI, 실행 구조, 디자인 토큰, 자산을 먼저 확인한다.
- 기존 놀이공원 테마가 있으면 이를 활용하고 거래소 구현·연동 어댑터는 trading 안에 둔다.
- 아직 UI가 없다면 향후 통합 가능한 최소 테마 UI와 연결 인터페이스를 구현한다.
- 루트 UI 수정이 필수라면 trading 안에 적용 가능한 패치와 절차를 준비한다.
- trading 외부를 임의 수정하지 않는다. 루트 UI에 실제 적용하지 않았다면 “연동 패치 준비”로 보고한다.
- 루트 UI 적용 여부와 무관하게 trading 내부의 독립 실행·시연은 완성한다.
- 한국어를 기본으로 한다. 티켓·전광판·어트랙션 테마를 활용하되 거래 정보의 가독성을 우선한다.
- 데스크톱에서 핵심 거래 정보를 한눈에 확인하고 작은 화면에서도 조작할 수 있게 한다.

필수 화면:
- 현재가, 기준가 대비 등락, 거래량.
- 매수·매도 호가와 가격별 잔량.
- 실제 체결에서 계산한 실시간 가격·거래량 차트.
- 최근 체결 내역.
- 주문 입력, 접수·처리 결과, 미체결 주문, 취소 기능.
- 계정의 휴가·포인트 보유량, 예약량, 사용 가능량.
- 봇별 전략, 연결·heartbeat, 주문 수, 체결 수.
- 연결 상태, 엔진 상태, 마지막 이벤트 순번.

실시간 데이터:
- 사용자와 봇은 동일한 검증·매칭 경로를 사용한다.
- UI 타이머로 가격·체결을 독립적으로 조작하지 않는다.
- 초기 상태 조회와 이벤트 구독 사이의 누락·중복을 처리한다.
- 이벤트 순번으로 중복을 제거하고 누락을 감지한다.
- 재연결 시 상태와 구독을 복원한다.
- 느린 클라이언트가 엔진 전체를 막지 않게 한다.
- 주문 접수, 확정 성공, 거절, 결과 미확인, 연결 단절을 사용자가 구분할 수 있게 한다.
- 브라우저에서 실제 주문·취소·체결·잔고 갱신을 검증한다.

## 9. 거래 봇 시연

거래 봇은 개발용 AI 에이전트와 별개인 로컬 거래 프로세스다.

- 기본 12개의 독립 봇 프로세스를 실행하고 최소 10개가 실제로 거래에 참여해야 한다.
- 각 봇은 고유 계정, 봇 ID, 전략, seed, 로그를 가진다.
- 마켓 메이킹, 유동성 소비, 추세 추종 등 여러 전략을 사용한다.
- 엔진 상태를 직접 수정하지 않고 공개 로컬 주문 API를 호출한다.
- 동일한 잔고·예약·자기 체결 방지 정책을 따른다.
- 합성 초기 자산과 전략을 조정하여 매수·매도·체결·취소가 지속적으로 관찰되게 한다.
- 봇 시작·중지·상태 조회를 제공한다.
- 수동 사용자도 봇과 같은 시장에 주문하고 체결할 수 있어야 한다.
- 활동 화면만 존재하고 실제 주문이 발생하지 않는 구현은 허용하지 않는다.
- seed, 초기 자산, 전략 설정, 실행 정보를 보존한다.
- 동시 실행의 정확한 재현은 기록된 엔진 입력 순서를 기준으로 한다. seed만으로 프로세스 스케줄링까지 재현된다고 주장하지 않는다.
- 온라인 시연의 봇 실행 위치와 연결 방법을 문서화한다. 실제 서버 환경에서 실행하지 않았다면 온라인 실행 완료로 보고하지 않는다.

## 10. 병렬 개발·작업 분할·구현 주기

개발용 하위 에이전트를 사용하여 독립 작업을 병렬 수행한다.

시작 시:
- AGENTS.md, Git 상태·기존 변경, 코드·UI·테스트·실행 구조를 확인한다.
- Rust·프런트엔드 런타임·브라우저·컨테이너 도구와 세션 로그 수집 가능 범위를 확인한다.
- 요구사항·의존관계·공통 주문·이벤트·오류·순번 계약을 정한다.
- 독립적으로 구현·검증 가능한 작은 작업으로 나눈다.
- 작업마다 담당자, 수정 파일 범위, 입출력 계약, 완료 조건, 검증 명령을 부여한다.

병렬 운영:
- 독립 작업이 있는 동안 환경이 허용하는 동시 슬롯을 최대한 활용한다.
- 호출·병합 비용만 늘리는 과도한 분할은 피한다.
- 같은 파일의 동시 편집을 피하고 공통 타입·프로토콜 변경은 조율한다.
- 주 에이전트도 직접 구현하며 통합·충돌 해결·전체 검증을 책임진다.
- 매칭·정산, 저널·복구, API·봇, UI·배포 준비를 초기 분담 후보로 사용한다.
- 슬롯이 부족하면 의존성이 해결된 작업부터 배정한다.
- 개발 에이전트 수와 거래 봇 수를 혼동하지 않는다. 실행하지 않은 에이전트를 기록하지 않는다.
- 성능 측정 구간에는 최대 병렬 실행의 예외를 적용한다.

마일스톤:
M0. 환경 점검, 가정, 계약, 작업 분할.
M1. 최소 엔진·API·UI의 주문→체결→화면 갱신.
M2. 예약·정산·취소·동시 요청·중복 방지.
M3. 저널·스냅샷·장애 복구.
M4. 놀이공원 UI와 12개 봇 통합 시연.
M5. 성능·할당 측정과 필요한 최적화.
M6. Vercel·엔진 배포 준비, 최종 검증, 문서·증거 정리.

작업마다 구현 → 관련 검증 → 실패 수정 → 증거 보존 → 문서·상태 갱신을 반복한다.
실패한 검증을 숨기고 완료 처리하지 않는다. 관련 없는 독립 작업은 계속할 수 있다.
통과한 검증을 새로운 변경이나 위험 없이 불필요하게 반복하지 않는다.
중요한 발견, 완료 항목, 다음 검증을 짧게 공유한다.

## 11. 테스트·성능 측정

거래 테스트:
- 가격·시간 우선순위, 부분 체결, 여러 호가 소진.
- 취소, 재취소, 체결·취소 경합, 다른 계정의 취소 거절.
- 잔고 부족, 잘못된 입력, 중복 요청, 같은 요청 ID의 내용 충돌.
- 자기 체결 방지, 용량 한계, 정수 경계·오버플로.
- 예약·해제·정산·가격 개선 및 전체 자산 보존.

동시성·복구·UI 테스트:
- 최소 12개 동시 클라이언트의 주문·취소.
- 고정 seed 무작위 명령과 불변조건 검사.
- 가능한 경우 단순 참조 모델과 결과 대조.
- 장애 주입 후 같은 확정 입력 범위의 정상 결과와 복구 결과 비교.
- 성공 ACK 보장, 미응답 요청 확인, 재시도 중복 방지.
- UI 이벤트 누락, 재연결, 상태 재동기화.
- 채택한 동시성 구조에 적합한 검증 도구 적용.

벤치마크:
- release 빌드, warm-up 이후 측정.
- CPU, OS, Rust 버전, 빌드 옵션, seed, 데이터 규모, 주문 분포, 동시성, 큐 용량, 저널 설정 기록.
- 성공 주문·취소·부분 체결·다중 체결을 포함하는 대표 부하 사용.
- 측정 전에 목표 부하·성능 목표와 근거 기록.
- 다음 결과를 분리한다.
  A. 순수 매칭·정산 코어.
  B. 내구성 보장을 포함한 주문 접수→성공 ACK.
  C. API 주문→클라이언트 이벤트 수신.
  D. 실제 배포 환경이 제공된 경우의 네트워크 포함 결과.
- 처리량, p50·p95·p99·최대 지연, 오류·거절률, 메모리 사용량, hot path 할당 횟수 측정.
- 측정 구간, 부하 발생 방식, 큐 대기 시간 포함 여부 명시.
- 정상 조건 벤치마크에서는 측정 대상·부하 발생기 외의 불필요한 봇·빌드·테스트 등 CPU·디스크 경쟁 작업을 일시 중지한다.
- 당시 주요 프로세스와 부하 조건을 기록하고, 자원 경쟁 스트레스 테스트는 별도 결과로 보존한다.
- 측정 후 병렬 개발과 시연을 재개한다.
- baseline과 최적화 결과를 같은 조건으로 비교하고 측정된 병목을 개선한다.

정직한 결과 보고:
- 코어 처리 지연, 내구성 포함 지연, 화면까지의 지연을 혼동하지 않는다.
- 로컬 성능을 인터넷 배포 성능으로 표시하지 않는다.
- 실측하지 않은 수치를 만들어내지 않는다.
- zero allocation과 lock-free는 확인한 범위만 주장한다.
- 실패·미달·미실행 항목에는 원인과 실제 검증 범위를 기록한다.

## 12. 문서·증거·실제 에이전트 기록

기존 문서 체계를 우선하되 다음 내용을 trading 하위에서 쉽게 찾을 수 있게 구성한다.

README:
- 준비 환경·의존성, 한 명령 로컬 시연 시작, 정상 종료.
- 테스트·벤치마크·장애 복구 시연 명령.
- 데이터 위치·보존 정책과 인계 방법.

설계·프로토콜:
- 구성 요소, 데이터 흐름, 주문·계정 상태 전이.
- 동시성·원자성·내구성 경계, 저널·스냅샷·복구, 성능 설계·한계.
- API·이벤트·오류·ID·순번·재시도·중복 방지·재연결.

ADR:
- 주요 아키텍처 결정, 대안, 선택 이유, 장단점, 변경 이력.
- 단순 오탈자 수정까지 별도 ADR을 만들 필요는 없다.

작업 상태와 누적 검증:
- 완료·진행·차단·다음 작업, 담당 에이전트, 체크포인트.
- run ID, 실제 명령, 실행 시각, 환경, 종료 코드.
- 성공·실패·미실행, 원본 출력·증거 경로, 실패 원인·수정·재검증.
- 성능 측정 조건·원본 결과·요약·한계.

배포 준비:
- Vercel Root Directory·빌드 설정·환경변수 예시.
- 공개·서버 전용 환경변수 구분.
- Rust 엔진 컨테이너 또는 실행 패키지, 영속 저장소 연결.
- 재시작·복구, HTTPS/WSS·Origin, 봇 실행 위치·접속 방법.
- 루트 UI 연동 패치·적용 방법과 실제 적용 여부.
- 실제 외부 배포 여부와 미검증 항목.

시연 자료:
- 사용자가 따라 할 수 있는 짧은 시연 순서.
- 실제 실행 화면 스크린샷, 가능하면 로컬 시연 영상.
- 엔진·API·봇 로그.

개발 에이전트 기록:
- 실제 에이전트 ID, 담당 작업, 시작·종료 시각, 결과.
- 도구가 제공하는 실제 세션 로그와 실행 출력을 가능한 범위에서 보존한다.
- 원본 로그와 작업 요약을 구분한다.
- 원본 export가 불가능하면 제한과 실제 수집 범위를 명시한다.
- 숨겨진 내부 추론이 아닌 실제 작업·도구·결과 기록을 보존한다.
- 존재하지 않는 세션·명령 출력·테스트 결과를 만들어내지 않는다.
- 로그와 문서에 비밀정보를 남기지 않는다.

관련 산출물은 작업 단위 완료 때마다 갱신한다. 마지막에 기억만으로 로그·ADR·검증 결과를 재구성하지 않는다.
