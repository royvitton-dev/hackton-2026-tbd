## 상태와 순서

`Core`는 네트워크, 파일, 시스템 시각, 난수, mutex를 사용하지 않는 단일 writer 상태 머신이다. `execute(Command)`에 전달한 timestamp만 사용한다. 가격별 `BTreeMap<u64, VecDeque<order_id>>`가 가격 우선과 같은 가격의 접수 순번 우선을 보존한다. 매수는 최저 매도부터, 매도는 최고 매수부터 순회한다. 체결 가격은 기존 maker 주문 가격이다. 주문과 체결의 전체 이력은 ID-1을 인덱스로 사용하는 Vec에 보존한다. 취소는 해당 가격 큐에서 주문을 제거한다. 취소의 같은 가격 큐 탐색은 O(해당 가격 주문 수)이며 자체 lock-free 구조나 unsafe를 사용하지 않는다.

`command_seq`와 `event_seq`는 신규로 접수한 명령마다 함께 증가한다. 일반 도메인 거절도 접수·저장되므로 증가한다. 주문 ID와 체결 ID는 각각 성공 주문 및 실제 체결에만 배정된다. 동일한 초기 상태, Config 및 순서가 정해진 명령은 같은 상태와 결과를 만든다. 순번·timestamp·금액은 JSON 안전 정수 상한 9,007,199,254,740,991을 넘지 않도록 제한한다.

## 자산과 원자성

3개 수동 계정 `user-01..03`, 12개 봇 계정 `bot-01..12`를 고정 생성한다. 각 계정은 1,000,000 모의 포인트와 1,000시간을 받으며 총량은 15,000,000포인트, 15,000시간이다. 합성 회사 표시는 사용자 지정대로 `GS리테이`, `GS칼테스`, `GS건썰`이다.

매수는 지정가×전체 수량의 포인트, 매도는 전체 시간 수량을 먼저 예약한다. 각 체결은 구매자의 지정가 예약분을 해제하고 실제 maker 가격을 판매자에게 이전한다. 차액은 구매자의 사용 가능 포인트로 즉시 반환한다. 미체결 부분은 원래 지정가로 예약을 유지한다. 취소는 남은 예약 전액을 해제하고 `cancelled` 수량을 누적한다. 계정 `orders_count`는 성공한 신규 주문만, `trades_count`는 매수·매도 각 계정에 체결 건수만 누적한다.

변경 전 별도 fill 계획과 15개 계정의 임시 숫자 잔고 배열을 계산한다. 부족 잔고, self-trade, 모든 체결 보존 용량, 누적값 및 예약 계산을 검증한 뒤 실제 거래 상태를 반영한다. 들어온 주문이 소진될 때까지 만날 상대 주문 중 자기 계정 주문이 하나라도 있으면 전체를 `SELF_TRADE`로 거절한다. 먼저 다른 계정의 유동성을 만나더라도 체결·정산은 남지 않는다. 소진 뒤 순서에 있는 자기 주문은 실행 대상이 아니므로 거절 사유가 아니다.

검증된 명령의 거래 상태는 한 `execute` 안에서 완성되며 외부 관찰은 반환 뒤 가능하다. 거절은 주문·체결·호가·잔고를 바꾸지 않지만 정상 접수 명령의 순번 및 중복 방지 결과는 기록한다. 메모리 부족으로 프로세스 자체가 중단되는 상황을 도메인 오류로 복구하는 보장은 없다. 저장 계층이 내구성 확보 후 공개를 책임진다. 순수 코어의 모든 반환값 및 저장된 결과는 `durable:false`다.

## 중복 방지와 용량

중복 키는 `(account_id, request_id)`이며 JSON 직렬화를 위해 계정→요청 ID의 중첩 문자열 BTreeMap으로 보존한다. 동일 키·동일 Action은 최초 결과를 `duplicate:true`로 반환하고 순번·자산·체결을 변경하지 않는다. 서버 timestamp는 Action 동일성에 포함하지 않는다. 동일 키·다른 Action은 `REQUEST_ID_CONFLICT`다. 충돌 결과의 순번은 원래 요청을 가리키며 새 이벤트를 만들지 않는다. 같은 요청 ID는 다른 계정에서 독립적으로 사용할 수 있다.

요청·주문·체결은 데이터셋 수명 전체에 걸쳐 보존하고 임의 만료·교체하지 않는다. 기본 상한은 주문 1,000,000, 요청 2,000,000, 체결 2,000,000이며 지정가 1~1,000,000, 수량 1~10,000이다. 상한은 Config에 있다. 주문/체결 용량 부족은 전체 명령을 거절하고 거절 결과를 보존한다. 요청 보존 용량이 찬 뒤 새로운 키는 `REQUEST_CAPACITY`로 **접수하지 않으며** 순번을 부여하거나 결과를 저장하지 않는다. 기존 키의 조회·중복 응답은 계속 가능하다. 용량을 더 크게 설정한 새 데이터셋으로 운영 전환할 절차가 필요하며 기존 보장 데이터를 삭제하지 않는다. 순번 상한도 같은 비접수 정책이다. 비어 있거나 128바이트 초과 요청 ID 및 64바이트 초과 계정 ID는 비접수 처리한다.

## 스냅샷과 비용

Serde 직렬화한 `Core`는 전체 주문·체결 이력, 가격 큐, 계정, 순번, Config, 중복 방지를 포함하는 복구 이미지다. 반복 사용하는 fill 임시 버퍼만 제외한다. `Core::snapshot()`은 UI용으로 최신 체결 1,000개와 모든 활성 주문 및 최신 종료 주문 200개만 제공한다. 잔고·누적 거래량·계정 건수는 전체 기간 값이다. UI에 없는 오래된 종료 주문도 복구 이미지에 남고 취소 시 정확히 `ORDER_NOT_OPEN`을 반환한다. 공개 스냅샷만 비교하면 숨겨진 이력 차이를 놓칠 수 있으므로 복구 동등성은 전체 직렬화 상태도 비교한다.

초기 주문/체결 Vec는 설정 상한 중 최대 4,096개, fill 임시 버퍼는 최대 256개를 사전 할당한다. Vec의 필요 용량 증가, 문자열/결과/중복 이력/가격 큐의 생성은 할당한다. 따라서 현 구현의 정상 hot path는 **zero allocation이 아니다**. 매칭 경로는 전체 종료 이력을 순회하지 않으며 실행 대상 가격 큐만 방문한다. 결과 직렬화·공개 스냅샷·I/O 비용은 순수 매칭 벤치마크와 별도로 측정해야 한다.

Order.status는 생성 시 최장 상태 문자열 길이인 16-byte capacity를 확보하고, 체결·취소 때 `clear`/`push_str`로 재사용한다. 복구한 기존 문자열의 capacity가 작으면 필요한 만큼 확장하며 저장 JSON·중복 결과·정산 의미는 유지한다. 동일 120,000명령 비교에서 할당 80,000회(4.4447%)를 줄였지만 요청 byte 합과 peak working set은 증가했고 속도 향상은 입증하지 못했다. 결과 String 및 dedup 깊은 복사는 여전히 할당한다. [정확한 측정 경계와 tradeoff](allocation-investigation.md)를 참조한다.

최소 체결 수량이 1이므로 한 명령의 fill 수는 해당 주문 수량 이하이며, 기본 설정에서 최대 10,000개다. 전체 체결 보존 용량도 적용한다. 임시 fill 및 응답 버퍼는 필요하면 이 검증된 수량까지 성장한다. 체결 보존 용량 부족은 모든 fill과 정산을 적용하기 전에 거절한다.

## 검증

`Core::check_invariants()`는 전체 이력을 감사한다. 총량 보존, 계정 예약량과 활성 주문의 일치, 원수량=체결+취소+잔량, 주문 상태, book FIFO/가격/활성 주문 일치, crossed book 부재, maker 가격/주문/계정 대응, 자기 체결 부재, 체결 수량 및 누적량/건수, dedup 순번 및 체결 결과의 일치를 확인한다. 전체 감사는 제출 hot path에서 실행하지 않는다.

`engine/tests/core_rules.rs`는 우선순위, 정산, 예약·취소, 권한, 중복·충돌, atomic self-trade, 용량, 정수 경계, 다중 체결, 전체 직렬화 및 공개 스냅샷 범위를 다룬다. 고정 seed 4개×1,000개 명령에서 매 명령 불변조건, 동일 입력 재생, 중간 직렬화 복원을 검사한다. `core_reference.rs`는 주문을 scan/sort하는 별도 단순 참조 모델과 3,000개 명령을 비교한다. 참조 모델은 총 보유량을 거래로 이전하고 예약을 주문에서 매번 재계산하므로 코어의 available/reserved 증감과 다른 경로로 검증한다.
