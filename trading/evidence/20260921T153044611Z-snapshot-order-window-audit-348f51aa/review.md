# 사용자 완료 주문이 공개 목록에서 사라지는 범위

읽기 전용 검토: 2026-09-22 00:30–00:33 KST. 기존 모바일 evidence와 현재 소스만 읽었고 API 호출·빌드·서비스 제어·운영 수정은 없다. 엔진 `65348c…6512`, core benchmark `7cfd820a…1a86`, aged recovery `d2c8dd9e…4d43` 파일의 SHA를 유지했으며 실행하지 않았다. 모든 읽은 입력의 SHA와 실제 산술은 `analysis.json`에 있다.

**두 주문의 누락은 시장 전체 terminal 200개 상한과 일치한다. 계정별 최근 완료 주문 20개를 보장하는 구현이 아니다.** 기존 `docs/ui.md:25`에도 봇 활동 뒤 수동 완료 주문이 이 탭에서 빠질 수 있다고 명시되어 있다. 공개 목록에서 빠지는 현상을 저장 이력 삭제나 durable ACK 유실로 해석할 근거는 없다.

## 정확한 소스 경계

| 범위 | 실제 동작 | 근거 |
|---|---|---|
| 공개 orders | 호가장에 있는 모든 활성 주문 ID + **전체 계정에서 ID가 가장 큰 종료 주문 200개**. 최종 배열은 ID 오름차순. | `engine/src/core.rs:11–12,523–549` |
| 종료 판정 | `remaining == 0`. 전체 체결과 취소가 모두 포함된다. | `engine/src/core.rs:534` |
| 공개 trades | 전체 Trade Vec의 마지막 최대 1,000개, 체결 ID/생성 순서를 유지한다. orders와 다른 window다. | `engine/src/core.rs:550` |
| UI 내 주문 | 받은 공개 orders를 계정으로 필터한 뒤 ID 내림차순 정렬. | `frontend/src/App.tsx:563–567` |
| UI 최근 완료 | 위 결과 중 `remaining == 0`을 골라 최대 20개. **전역 200개 제한 이후** 적용하므로 내 주문 0개도 정상적으로 나온다. | `frontend/src/App.tsx:569–571` |
| 화면 안내 | 탭 제목은 “최근 완료 주문”. 빈 경우 “최근 조회 범위에 완료 주문이 없어요”와 브라우저의 “요청 결과” 탭을 안내한다. | `frontend/src/App.tsx:759–765,846–858` |

여기서 “최근”은 **완료 시각 순서가 아니라 주문 생성 ID 순서**다. `orders.iter().rev().filter(remaining==0).take(200)`이며 Order에는 최초 `command_seq`/`timestamp_ms`만 있고 별도 완료 순번/완료 시각 필드는 없다(`model.rs:62–74`). 예를 들어 낮은 ID 주문이 오래 대기하다 방금 취소되더라도 더 높은 ID의 종료 주문이 이미 200개면 완료 목록에 나타나지 않을 수 있다. 이것은 이번 모바일 run에서 별도로 재현한 새 시나리오가 아니라 소스에서 직접 도출되는 범위 제한이다.

## 요청 결과는 현재 주문 상태와 별개

별도 fallback인 “요청 결과”는 immutable command ACK다(`docs/protocol.md:20`, `App.tsx:350–381`). #115979는 후속 명령 #133076에서 체결됐지만 최초 주문 응답 #133026의 `trades:[]`는 바뀌지 않는다. 실제 reload DOM도 이 주문에 “호가장에 접수”를 표시한다. 해당 응답은 접수 당시 사실을 말하며 “지금 미체결”을 뜻하지 않는다. 이 요청 결과를 최신 filled/cancelled Order로 합성하면 잘못된 상태를 만들 수 있다.

또한 `protocol.ts:64–66`의 20개 확정 요청 보존은 **브라우저/API URL별 전체 records의 상한**이고 계정별 quota가 아니다. `useExchange.ts:15–18,42–48,165–168`에서 저장·갱신한 뒤 `App.tsx:572`에서 선택 계정을 필터한다. 미확인/제출 중 요청은 20개 제한에서 제외된다. 이번 모바일의 세 요청은 보존되어 있지만 다른 모의 계정으로 확정 요청을 많이 보내면 같은 브라우저의 오래된 user-03 요청도 표시 범위 밖이 될 수 있다. 현재 문서는 “브라우저 요청 결과 최근20개”로 표현하여 이와 모순되지 않는다.

## 문서와 UX 판정 및 최소 개선안

**이미 명시된 제한:** `docs/core.md:33`, `docs/protocol.md:26`, `docs/ui.md:25`는 공개 이력을 bounded view로 설명한다. 특히 UI 문서는 전역200개와 사용자 주문 탈락을 명시한다. 계정별 완료 20개 보장이나 전체 이력 UI를 약속한 문구는 이 검토 범위에서 찾지 못했다. 현재 빈 목록 안내도 단순히 “주문이 없다”고 단정하지 않는다.

**남은 작은 문구 모호성:** 탭 제목만으로는 사용자가 “내 최근 완료 20개”를 기대할 수 있고, “최근 완료”는 완료 시각순으로 읽힐 수 있다. 다음 정도의 표시 보완이면 데이터 계약·공개 payload·운영 메모리 변경 없이 범위를 더 정확하게 설명할 수 있다.

1. 완료 탭에 상시 보조 문구: “시장 전체의 주문번호 기준 최근 완료 200건 중 내 주문을 최대 20건 표시합니다.” 문서의 “최근 종료 주문”도 주문번호 기준임을 덧붙인다.
2. 요청 결과에는 “요청 처리 당시 결과입니다. 이후 체결·취소 상태와 다를 수 있습니다.”를 안내하거나 기존 “호가장에 접수”를 “접수 당시: 호가장에 접수”로 명확히 한다. 접수 ACK로 최종 상태를 추정하지 않는다.

계정별 최근20개를 **실제로 보장**하려면 별도 제한된 계정 이력 계약/조회가 필요하므로 문구 수정과 다른 작업이다. 이번에는 새 API, 전체 history 공개, terminal 상한 증대, 로컬 ACK로 Order 상태 합성, 운영 소스 변경을 제안의 즉시 적용 범위에 넣지 않는다. 정확성·복구·wire 계약을 바꾸지 않는 위 두 안내가 가장 작은 조치다.
